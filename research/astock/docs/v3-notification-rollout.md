# v3 通知展示接入

## 范围

`config/notifications.json` 的 `reportView: "research_brief_v3"` 只影响新建的日常成功通知附件。现有单条 Telegram 消息与 Markdown 附件方式不变：固定说明文字指出四问正文和完整来源在附件，附件首屏是简报，后面保留原始研究全文。

不改变研究生成、密封、relay、目标会话、发送时间、模型、股票池及更正报告。没有新增自动静日判定，也没有“查看详情”网页或按钮。本次获批接入，不代表实际通知已发送或次日自然窗口已验收。

## 兼容与核验

- `src/report-presentation.mjs` 对已知的 `results_only_v1` 和 `research_brief_v3` 做显式分派；未知版本拒绝。
- 新事件分别保存展示稿 `sha256/bytes` 和原稿 `sourceSha256/sourceBytes`。发送前、回执确认时继续核对原稿及确定性渲染结果。
- 旧事件按自身 `presentation` 校验，不按当前配置重渲染。无 `presentation` 的旧全文事件保持原字节。回执格式不变，不补造历史回执。
- 每日事件 ID 的 `telegram-v1` 后缀是去重身份，不是展示版本，保持不变。切换配置不能使已发出或不确定事件重新入队。
- v3 渲染失败拒绝投递，不回退全文、不发送替代失败通知。
- 已有 `results_only_v1` 渲染器不可改写；v3 上线后若输出规则需要变化，应使用新展示版本，不能让旧回执的重算结果变化。

## 发布步骤

1. 核对生产 HEAD 和工作区；只在预期基线且工作区干净时应用经过测试的补丁。
2. 先在独立发布目录使用 Linux 网络隔离运行配置检查和全套测试，全部通过才改生产源码。
3. 应用代码和配置变更，不执行通知命令、生成任务、密封任务或 relay；一次性通知服务在下一次正常触发时读到新版本，无需重启或补跑。
4. 只读核对现存历史事件、回执、原报告及密封未改变，验证当前报告能渲染。当前历史回执仍按旧版本确认；不把它算作 v3 真实触达证据。
5. 记录实际提交与测试结果。下个自然窗口的 v3 新附件、回执绑定及用户阅读体验仍需实际验收。

## 回退

将 `reportView` 改回 `results_only_v1` 即可让之后新建事件使用 v1；保留已发布的 v3 读取和核验代码，以便核对已经存在的 v3 事件。不要删除、重写、重命名任何通知事件／附件／回执来强制重发。

如果在生产应用后、尚未产生任何 v3 事件之前发现代码问题，可按本次提交的精确差异回退源码；已有 v3 事件时不得直接移除其解析器。不得用整目录覆盖或重置丢弃用户的后续变更。

## 测试

新增 `test/v3-delivery.test.mjs` 使用临时目录与假发送器，覆盖密封准备、版本分派、原稿和附件的双重哈希、回执绑定、无写入检查、伪造拒绝、配置前进／回退以及重复调用不重发。既有 full/v1、更正、并发、发送不确定性测试仍须全量运行。真实演练不在本次操作范围。
