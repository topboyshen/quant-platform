## 两个已复现的收益计算问题

实验复用 [M4 结果测试](../backend/tests/test_m4_outcomes.py) 的 `decision()`、`code_bars()` 和 `benchmark_bars()`，截止日统一取 `SESSIONS[-1]`。日期为测试构造的交易日。每一行只改变表中列出的一项输入。

| 输入 | 基线上的实际输出 | 影响 |
| --- | --- | --- |
| 行情完整 | 三日结果为 `filled`，2027-03-02 开盘入场，03-04 收盘出场 | 对照组 |
| 去掉 03-02 的基准日线，标的行情完整 | 同为 `filled`，入场变为 03-03，出场变为 03-05 | 入场和出场均换日 |
| 去掉 03-03 的基准日线，标的行情完整 | 同为 `filled`，入场仍为 03-02，出场变为 03-05 | 中间只缺一天也会改变观察窗口 |
| 基准完整，将标的入场日设为开收盘 10、最高 9、最低 11，再执行 `normalise_bars` | 一日结果仍为 `filled`，最大有利波动为 −10.045%，最大不利波动为 +9.945% | 自相矛盾的价格能生成收益及波动指标 |

在记录链模式下，`_filter_due` 用交易日历判断到期，`evaluate_decision` 用实际收到的基准日线排列日期。两者在基准缺数时分歧。`_persist` 对已有「决策、期限」组合跳过写入，因此普通重跑也不会自动纠正已经记下的日期。代码注释明确记录了与旧版逐行对账的约束，修复应保留旧口径供比较。

## 优化顺序与验收

| 顺序 | 建议工作 | 达标条件 |
| --- | --- | --- |
| P1 · 收益窗口 | 由后端信号模块按交易日历确定入场日和期限日。为基准缺日记录待补原因。先在 MS02u 同一批冻结输入上跑新旧口径，列出受影响的决策和期限。 | 上表两组缺日输入均能暴露数据缺口，不能作为正常成交顺延。数据补齐后日期和收益与完整输入一致，连续重跑两次只有一份有效结果。已写入结果的修订可追溯，保留原记录。 |
| P1 · 行情有效性 | 在行情解析和结果计算共用的校验中约束最低价 ≤ 开盘、收盘 ≤ 最高价。隔离无效行并记录标的、来源、日期与原因，把缺数状态传给下游。 | 倒置高低价、开盘越界、收盘越界三组用例均无法生成已成交指标。合法平盘仍进入原有流动性判断。补齐数据后与正常样本对齐，完整行情的历史对账仍通过。 |
| P1 · 发布口径 | 由文档维护者将标为“当前”的版本、冻结起点和最早复核日集中到冻结基线。中文 README 和退役路线图引用该处，历史发布保留日期与收据。 | 对照 [中文 README §6、§8](../../README.zh-CN.md) 的 `.115/.116` 和 [退役路线图开头](DECOMMISSION-ROADMAP.md) 的 12-08，修订后各入口对同一时点只给出一个版本和复核日。 |
| P2 · 恢复与退役证据 | 运维先确定允许的恢复时间与数据损失窗口。在隔离宿主从异地副本恢复，逐段计时到浏览器可用。准备退役的每个服务另列消费者、替代路径与回滚证据。 | 演练记录副本时间、最后完整交易日、迁移、API、页面和调度检查，以及总耗时与约定目标的比较。缺验收项时标明未完成。逐服务按 [M9 清单](M9-EXECUTION-CHECKLIST.md) 复核。 |
| P2 · 类型检查 | 在仅报告的模块中先选一个错误数可控的模块，记录已有错误，再将新增错误设为阻断条件。 | 临时引入一处类型错误可使检查失败，撤销后恢复通过。原有关键模块仍通过；该模块既有错误清零后加入现有阻断列表。 |

按冻结基线，文档校正与本地影子验证可先做。收益语义调整先评估影响，再按发布流程评审。基线给出的 M9 Phase 2 最早复核日是 2026-12-09，届时需重新核对实际运行证据。

## 本机验证

基线在 MS02u 上使用 Python 3.12、独立 PostgreSQL 测试数据库和 Node 22。后端在 `app/backend` 下执行 `python -m pytest -q --run-assets -ra`，**586 项通过**。前端按锁文件安装依赖后执行 `npm test`，**67 项通过**；`npm run lint` 和 `npm run build` 均通过。构建中 Naive UI 包为 824.17 kB，高于仓库的 700 kB 告警线。当前没有首屏耗时样本，拆包优先级应以页面实测决定。
